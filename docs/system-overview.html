Game Boy DMG Emulator

How the system works today: cartridge loading, memory bus, and the SM83 register file

C++17 · CMake + Ninja · MinGW-w64 g++ on Windows · SDL2 linked, not yet used  |  Source: src/bus.hpp, src/cpu.hpp, src/main.cpp, tests/cpu_tests.cpp

1.Where the project stands

The emulator is built bottom-up. Three layers exist: a cartridge image in memory, a bus that addresses it, and a CPU register file that knows its own post-boot state. Nothing executes instructions yet — there is no fetch, no decode, no cycle counter. What runs today is a host-side program that proves the lower layers are correct:

  1. Read a real ROM file from disk into memory (no fake placeholder buffer).
  2. Parse and validate the cartridge header from that memory.
  3. Address the ROM through the bus, exactly as the CPU eventually will.
  4. Initialise a register file to the exact state the DMG boot ROM leaves behind.
  5. Verify all of the above with an independent test executable.

2.Architecture

The dependency direction is strictly downward: the CPU will never know that a file on a Windows disk exists, and the bus never knows who is reading from it.

Why the split matters. Nintendo's hardware has one shared 16-bit address bus; ROM, RAM and I/O all live in the same 64 KiB window. Modelling the bus as a separate object (rather than letting the CPU index an array) is what makes cartridge mappers, VRAM and the PPU addable later without rewriting the CPU.

3.What happens when you run it

gbemu.exe [rom-path] — with no argument it defaults to roms/cpu_instrs.gb. The whole run is eight steps:

#StepWhat actually happens
1Parse the command lineargv[1] if present, otherwise the default ROM path.
2Open and size the filestd::ifstream in binary mode with std::ios::ate, so the length comes from tellg() without a seek-guess.
3Read into a bufferA std::vector<uint8_t> of exactly the file's length; the whole image is read in one call.
4Build a RomThe vector is moved in (no copy), then the header is parsed once — not on every read.
5Attach to the busbus.attach_rom(&*rom) stores a non-owning pointer; the Rom stays owned by main.
6Print the header blockTitle, entry bytes, size check, cart type, RAM size, checksum verdict.
7Prove the bus worksPrint the byte at 0x0000 — read through the bus, not from the vector.
8Return0 on success, 1 with a message on stderr if the ROM could not be loaded.

4.Cartridge header decoding

Everything below comes from bytes already in memory, addressed by constants in RomHeader rather than magic numbers scattered through the code.

AddressFieldDecoding
0x0100–0x0103Entry pointFour raw bytes built into a uint32_t and printed as bytes. On this ROM 00 C3 37 06 is NOP then JP 0x0637, which is exactly why they are not printed as one number.
0x0134–0x0143TitleUp to 16 ASCII bytes; stops at the first 0x00, trailing spaces trimmed, empty title becomes UNTITLED. A truncated file stops at its real end instead of reading past it.
0x0147Cartridge typeByte mapped to a mnemonic table: 0x01 → MBC1, 0x13 → MBC3+RAM+BATTERY, 0xFF → HuC1+RAM+BATTERY, unknown codes → UNKNOWN.
0x0148ROM size code0x00–0x08 → 32 KiB << code; 0x52/0x53/0x54 → the odd 1.1/1.2/1.5 MiB carts. Compared against the real file length, so a truncated or padded dump is reported as MISMATCH.
0x0149RAM size code0x00 none, 0x01 2 KiB, 0x02 8 KiB, 0x03 32 KiB, 0x04 128 KiB, 0x05 64 KiB (note the last two are out of order in the spec).
0x014DHeader checksumStored byte, compared with one recomputed at load.

The checksum algorithm

Over 0x0134 to 0x014C inclusive, the running value starts at zero and for each byte does x = x - byte - 1, in the arithmetic of an 8-bit register. The subtract-and-decrement form is what the boot ROM itself does; the -1 is not a typo for x - byte. In C++ that is one line per byte with a cast back to uint8_t, so the wrap-around is the hardware's wrap-around:

uint8_t x = 0;
for (size_t addr = 0x0134; addr <= 0x014C; ++addr) {
    x = static_cast<uint8_t>(x - read(addr) - 1);
}
hdr.computed_checksum = x;
hdr.checksum_ok = (x == hdr.checksum);
This is a real check, not a formality. On cpu_instrs.gb the recomputation produces 0x3B and the stored byte is 0x3B, so the run prints PASS. If a dump were corrupt, the same line prints 0x3B next to a different stored value and says FAIL — the emulator would not be blamed for bad input.

5.The memory bus

Bus owns a 16-bit-addressable view of the machine. A byte read asks "which device lives at this address?" and forwards the request; a write is ignored unless something writable is there. Unmapped space reads 0xFF, which is what an unconnected data bus floats to.

Address rangeDeviceBehaviour today
0x0000–0x7FFFCartridge ROMRead: forwarded to the Rom at the same offset. Write: ignored (ROM is read-only).
0x8000–0x9FFFVRAMUnmapped → reads 0xFF.
0xA000–0xBFFFCartridge RAMUnmapped → reads 0xFF.
0xC000–0xDFFFWRAM, 8 KiBRead and write, zero-filled at construction. Offsets are addr - 0xC000.
0xE000–0xFDFFEcho of WRAMUnmapped → reads 0xFF.
0xFE00–0xFEFFOAM (sprites)Unmapped → reads 0xFF.
0xFF00–0xFFFFI/O, HRAM, IEUnmapped → reads 0xFF.

Two deliberate simplifications, both safe while nothing executes instructions:

  • No MBC banking. 0x4000–0x7FFF reads the same linear file offset instead of switching to a cartridge bank. On a 32 KiB ROM that is correct by accident (there is only one bank); on an MBC1 cart it is the wrong bank past 0x3FFF. This is the first thing the mapper work has to fix.
  • Unmapped reads return 0xFF rather than trapping. That keeps the bus total: every address answers, so the CPU can be dropped on top without null checks.

6.The CPU register file

The SM83 is an 8-bit CPU with an address space of 16 bits, so it has eight 8-bit registers that can be paired into four 16-bit ones. Cpu today is that state and the rules for reading and writing it — nothing more.

PairHighLow
AFAF (flags)
BCBC
DEDE
HLHL
FlagBitMeaning
Z0x80zero result
N0x40subtract (for BCD)
H0x20half carry (bit 3)
C0x10carry / borrow

Design decisions worth knowing

  • Pairs are computed, never stored. af() recombines a_ and f_ each time. Storing both views would allow the 16-bit and 8-bit versions of the same register to drift apart — a bug class that would be very hard to see.
  • Only the high nibble of F exists. On real hardware bits 0–3 of F are not connected. FLAG_MASK = 0xF0 is applied inside set_f() and nowhere else, so every path that writes flags — including set_af() and set_flag() — funnels through one choke point and cannot leak junk bits.
  • AF is masked, HL is not. AF carries the flag nibble; HL is a plain 16-bit register, so masking it would be wrong.
  • Flag readers are z_flag(), n_flag(), h_flag(), c_flag(). h() and c() are already the H and C registers, so one name could not mean two things.

Post-boot state, and why those numbers

The plan skips the boot ROM, so the CPU must start where the boot ROM would have left it. These are the DMG values from Pan Docs, verified against the power-up table rather than recalled:

RegisterValueOrigin
AF0x01B0A = 0x01 (the value written to 0xFF50 to unmap the boot ROM); F = 0xB0 = Z=1, N=0, H=1, C=1
BC0x0013B = 0x00, C = 0x13
DE0x00D8D = 0x00, E = 0xD8
HL0x014DH = 0x01, L = 0x4D
SP0xFFFEtop of HRAM
PC0x0100first byte of the cartridge entry point
The one conditional value. Pan Docs lists H and C as "?" with a footnote: both are set unless the cartridge header checksum byte is 0x00, in which case both are clear. cpu_instrs.gb has 0x3B, so F = 0xB0. A dump with a zero checksum would boot with F = 0x80. POST_BOOT_AF is hardcoded to the normal case, which is correct for every ordinary dump — and these are DMG numbers: the MGB boots with A = 0xFF, the SGB with C = 0x14 and HL = 0xC060, the CGB with A = 0x11, BC = 0x0000, DE = 0x0008, HL = 0x007C.

7.How correctness is checked

tests/cpu_tests.cpp is a second, standalone executable — it does not link against gbemu, so a broken test cannot break the emulator build and vice versa. It uses plain <cassert>: a failed assertion aborts the process with a non-zero exit code, which is all CTest needs. #undef NDEBUG appears before the include so the checks survive even in an optimised build, where assert would otherwise expand to nothing.

TestWhat it pins down
pair_accessors_testWriting 0x1234 to BC puts 0x12 in B and 0x34 in C; writing C afterwards makes bc() return the new pair. Proves the pair is recombined from the bytes, not cached.
af_masking_testset_af(0xFFFF) yields 0xFFF0; set_f(0x0F) yields 0x00. Writing F directly is not a back door into the low nibble.
flags_testEach flag toggles independently, clearing one leaves the other three intact, re-setting a set flag is a no-op, and the four mask constants equal their documented bit values.
reset_testScrambles all registers, calls reset(), and asserts the full DMG post-boot table. Also asserts that a freshly constructed Cpu is already reset, so the constructor cannot silently regress.

8.Verified versus not yet true

Verified working

  • Real 64 KiB ROM loads from disk; missing file exits 1 with a message.
  • Header fields match the file: title CPU_INSTRS, size code 0x01 matching 65,536 bytes, MBC1.
  • Header checksum recomputes to the stored 0x3B and reports PASS.
  • Bus reads a byte from ROM at 0x0000 (0x3C) and round-trips WRAM.
  • Register file: pairs, flags, masking and post-boot reset() all asserted.

Not true yet

  • No instruction fetch, decode or execute — PC never advances.
  • Cpu is not connected to Bus; main uses each separately.
  • No cycle counting, no interrupts (IME/IF/IE), no HALT/STOP.
  • No cartridge banking; VRAM, OAM, I/O and HRAM are unmapped.
  • SDL2 is linked but no window or framebuffer exists.
  • Tests run on demand, not automatically as part of the build.

9.What comes next

The next step is the first instruction loop: give Cpu a reference to Bus, read the opcode at PC, advance PC, and dispatch through a 256-entry table to implementations that set flags exactly as the SM83 does. The register file is already the right shape for that — it exposes byte and pair accessors and a single flag choke point — so the instruction layer adds behaviour without changing the state model.
